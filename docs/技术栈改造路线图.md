# 技术栈改造路线图（4周 / 8周 / 12周）

生成日期：2026-09-10

本文以“当前项目技术现状（React+Vinext+Cloudflare D1/R2 与独立 Django 服务，正式数据库目标为 PostgreSQL）”为基础，给出可执行分阶段改造计划。

## 目标与约束

### 总体目标

- 把“可开发可演示”提升为“可观测、可恢复、可上线、可运维”。
- 保持现有产品能力不倒退，优先保证支付、积分、订单、身份、内容与视频链路稳定。
- 每阶段只完成可验收的交付，不一次性重构整个系统。

### 阶段原则

- P0：影响线上可用性的关键项，必须在 4 周内完成。
- P1：影响稳定性与商用闭环的关键项，在 8 周内完成。
- P2：性能、规模与治理优化，在 12 周完成。

---

## 第 1 阶段（0-4 周）：先把关键链路打稳（P0）

### 1) 交付项（按优先级）

1. 交易与数据一致性基础线
- 建立跨服务幂等与恢复总线：
  - 网站订单接口：对每个订单请求引入 `idempotency_key`。
  - D1 与 PostgreSQL 的关键状态变更写入“待处理表/补偿记录”。
  - 统一定义订单状态机（待支付 / 待审核 / 已付款 / 已发货 / 已完成 / 已关闭 / 异常）。
- 给所有库存扣减、积分变更、订单变更加上幂等保护。

2. 任务和告警最小闭环
- 将订单过期、积分补偿、订单恢复从“有脚本可跑”升级到“可持续重试”。
- 给现有脚本增加重试上限、失败告警、执行日志和重试时间窗口。
- 建立失败队列与告警阈值（例如 5 分钟内失败率 > 2% 告警）。

3. 认证与会话安全收敛
- 梳理 `geo_staff`、`geo_visitor`、Django staff-session 的会话边界并统一失效策略。
- 明确服务间 Bearer 凭据轮换和失效流程。
- 对关键管理接口补齐权限细分与最小授权原则。

4. 支付链路可控化（阶段性）
- 先完成“未启用支付”状态下的状态校验保护（避免前端展示与后端状态不一致）。
- 建立支付能力开关和开关影响范围文档（网站端、管理端、API、日志）。

5. 生产化环境基础设施起步
- 制定 Django 运行生产模式清单：
  - 进程托管策略、服务健康检查、启动失败重试。
  - 日志标准化（请求 ID、trace id、关联订单 ID）。
  - PostgreSQL 连接池、慢查询阈值、只读副本读写分离策略。
- 记录并确认 `wrangler` 本地运行与生产运行差异边界。

### 2) 风险与对策

- 风险：跨数据库（D1 与 PostgreSQL）无 ACID 引发库存或积分漂移。
- 对策：幂等 + 审计日志 + 异常补偿表 + 人工处理兜底。

- 风险：脚本任务异常重复执行导致双计扣。
- 对策：任务日志唯一键 + 幂等状态锁 + 一致性检查任务。

- 风险：现有 API 响应与错误码不一致。
- 对策：先定义统一错误码（`PENDING`、`INVALID_STATE` 等）并灰度输出。

### 3) 验收指标（本阶段）

- 订单核心链路 7 天内“异常补偿/人工介入”不高于历史峰值的 50%。
- 订单接口幂等成功率（同一 idempotency_key 重复请求）达到 99.9%。
- 订单、积分、库存状态转换有可追溯日志（每次失败可回溯到请求 ID + 订单 ID + 业务层动作）。
- 关键管理接口未授权访问拦截成功率 100%。

---

## 第 2 阶段（5-8 周）：形成可上线闭环（P1）

### 1) 交付项（按优先级）

1. 支付闭环（第一性优先）
- 完成微信支付全链路（或替代支付方式）可回放路径：
  - 预下单、回调、签名验签、异步回调幂等。
  - 关单、退款、对账作业。
- 增加支付状态同步守护（异步核对对账，不依赖前端回调单点）

2. 统一 API 契约与错误治理
- 形成统一响应结构（`success`/`code`/`message`/`data`/`traceId`）。
- 统一分页、列表排序、字段校验策略。
- 逐步改造对外公开接口，优先改造：订单、订单历史、积分、素材、管理员操作。

3. 生产数据库与持久化增强
- 落地 Django 业务库 PostgreSQL 生产方案（schema、连接、安全、备份、迁移）。
- 交付 PostgreSQL 运行配置：连接池、连接超时、事务隔离等级、主从/副本策略与故障切换演练。

4. 监控与告警
- 建立统一监控条目：
  - 接口错误率、P95 延迟、任务队列堆积、支付成功率、登录失败率。
- 告警规则：
  - 关键接口错误率、任务重试失败率、支付回调异常率、存储上传失败率。

5. 内容与视频交付治理
- 建立资产发布校验规则（图片/video 体积、码率、时长、封面、访问控制）。
- 视频资源加密密钥和签名 URL 生命周期标准化。

### 2) 风险与对策

- 风险：支付与订单状态机出现边界缺口。
- 对策：状态机覆盖全部转移事件并增加“不可逆状态”检测。

- 风险：数据库迁移窗口长，影响稳定性。
- 对策：双写/回放验证、灰度切换、数据库回退演练、最小化锁定窗口迁移脚本。

- 风险：前端多端（网站+小程序）对支付/订单状态处理不一致。
- 对策：统一状态字典与状态变更广播到多端。

### 3) 验收指标（本阶段）

- 支付回调处理成功率 ≥ 99.5%（测试 + 模拟 + 灰度环境）。
- 订单状态一致性：网站与 Django 侧同一订单最终状态不一致率 = 0（按日对账）。
- 接口错误率（P0 API）持续 7 天 < 1%。
- 关键告警 95% 可在 15 分钟内通知到位。

## 第 3 阶段（9-12 周）：体系化优化与规模化准备（P2）

### 1) 交付项（按优先级）

1. 可扩展部署与运维标准化
- 完成生产部署基线（容器化 / 运行编排 / 回滚策略）。
- 明确站点 Worker、Django 服务、任务处理器的版本发布流程（含停机与回滚）。

2. 任务系统升级
- 引入标准任务队列（按需求选择成熟队列系统）并将高频/重任务迁移。
- 支持任务可观测（重试次数、耗时分位数、死信队列）。

3. 全链路可观测性与追踪
- 引入请求链路追踪（前端->网站 API->Django->存储）。
- 建立统一日志 schema 与审计检索（按订单、用户、渠道、时间段）。

4. 性能与体验优化
- 对高频接口实施缓存策略（公共内容、分类、导航、公共配置）。
- 首页/列表首屏加载预算、图片加载策略、HLS 起播时延优化。
- 小程序端与网站端共享请求层错误提示与重试策略。

5. 质量体系
- 建立端到端回归清单：
  - 下单、核销、积分、退款、登录、权限、视频播放、内容发布。
- 扩展 API 与关键页面自动化回归，形成每周回归节奏。

### 2) 风险与对策

- 风险：升级任务系统期间出现重复执行。
- 对策：新旧队列双写监测 + 只读回放 + 分阶段切流。

- 风险：部署平台与现有 Cloudflare / D1 / R2 链路不完全匹配。
- 对策：提前建立变更矩阵（功能、环境、回退方案）并在预发布演练。

- 风险：观测数据缺失导致问题定位慢。
- 对策：日志与 trace 强制字段化（`traceId`，`requestId`）在所有对外服务入口。

### 3) 验收指标（本阶段）

- 生产环境发布可在 30 分钟内回滚（含数据库回退预案）。
- PostgreSQL 备份与恢复演练达到 RPO <= 5 分钟、RTO <= 30 分钟。
- 核心链路（订单、支付、积分、登录）故障平均恢复时间（MTTR）≤ 60 分钟。
- 任务系统 95% 任务在 SLA 窗口内完成处理。
- 全链路回归用例每周执行通过率 100%，并保留失败复测记录。

---

## 每阶段固定输出（所有阶段都要产出）

- 《阶段交付清单》：含已完成/未完成项。
- 《风险日志》：新出现风险、责任人、闭环时间。
- 《验收记录》：指标截图/日志、测试报告、异常样本。
- 《下阶段计划》：基于实测数据调整范围。

---

## 建议的实施顺序（可按“最短反馈回路”执行）

- 先做“订单一致性 + 幂等 + 异常补偿 + 告警”
- 再做“支付闭环 + API 契约 + 权限收敛”
- 最后做“部署标准化 + 任务队列 + 统一监控+回归体系”

你可以先从本周开始执行第 1 阶段。先定一个时间盒：
- 每周一次里程碑复盘（验收指标是否达标）
- 每周只冻结一个 P0 风险项
- 每周末提交一次可回滚的增量。
